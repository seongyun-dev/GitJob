# Career Collector V1

커리어(`job.career.co.kr`) 채용공고를 `job-analysis-input/v1`(S15P21E102-90)
배치로 수집합니다. 공용 수집 계층(S15P21E102-99)을 쓰므로 워크넷·사람인·게임잡과
같은 계약·같은 정규화기를 통과합니다.

| 항목 | 값 |
|---|---|
| `source_site` | `CAREER` |
| `collector_version` | `career-collector/v1` |
| 목록 | `GET /jobs/jobpart?i_jc1={대분류}&page={n}&i_pagesize=30&i_so=3` |
| 상세 | `GET /recruit/view/{id}` |
| 인코딩 | UTF-8 |
| 요청 간격 | 기본 2.0초 |
| 공고당 요청 | **1회** (상세 본문이 HTML 안에 있음, iframe 없음) |

## 기준 A 미통과 — 먼저 읽으십시오

**커리어는 기준 A를 통과하지 않았습니다.** 기준은
`docs/data/2026-08-31-jobkorea-retention-decision.md` §4이고, 2026-09-09 실측
결과입니다.

| 항목 | 실측 |
|---|---|
| 운영사 | **(주)커리어넷**, 사업자등록번호 **220-86-73547** |
| 판례 근거 | **적용 안 됨** — 잡코리아/웍스피어(110-81-34859)와 별개 법인 |
| robots.txt | **허용** — `/admin` `/app` `/base` `/biz` `/user` `/signup`만 차단, `sitemap.xml` 공개 |
| 이용약관 | **제14조 5항 위반 소지** |

> 제14조 5항 — "이용자는 커리어서비스 이용을 통해 획득한 정보 및 게시물을
> 커리어넷의 **동의없이 복제, 배포할 수 없으며** 상업적, 영리목적으로 이용할 수
> 없습니다." (제20조 6·7항 동일 취지)

기준 A는 **OR 조건**입니다. robots.txt가 허용해도 약관이 금지하면 미통과입니다.
공고를 HDFS에 적재하는 것은 복제에 해당합니다.

크롤링·스크래핑을 **명시적으로** 금지하는 조항은 없습니다 — 링커리어(이용약관
제20조가 스크래핑을 직접 금지)보다는 약합니다. 그러나 금지는 금지입니다.

**이 수집기는 위 조항을 확인한 뒤 소유자가 진행을 결정해 만들어졌습니다.**
그 근거는 각 회차 manifest의 `source_admission` 블록에도 기록되므로, 배치가 이
레포보다 오래 남아도 어떤 근거로 수집됐는지 알 수 있습니다.

`schedule.toml`의 두 회차는 `enabled = false`입니다. 소유자 결정은 일회성 수집에
대한 것이었고 하루 2회 자동 회차는 별개 판단이라, 켜는 것이 물려받은 기본값이
아니라 의도적인 행위여야 합니다.

## 이 사이트가 왜 수집 가치가 있나

**마감된 공고가 목록에서 사라지지 않습니다.** 2026-09-09 실측으로 H0 2페이지에
2026-06-15 등록 공고가 살아 있었습니다. 30행 중 24행이 `상시채용`입니다.

워크넷은 마감 공고를 내려서 어느 시점에 보든 최근 2개월분만 존재합니다 —
2026-02-01~03-31 구간을 요청했을 때 **0건, "listing exhausted"** 였습니다.
커리어는 그보다 긴 기간이 남아 있어 과거 시계열을 조금 더 확보할 수 있습니다.

## 두 개의 대분류가 필요합니다

`i_jc1`이 직종 대분류를 **서버측에서** 필터합니다. 개발 공고는 두 곳에 나뉩니다.

| 코드 | 이름 | 2026-09-09 실측 |
|---|---|---|
| `H0` | IT.인터넷 | 8페이지에서 끝, **227건** |
| `N0` | 연구개발.엔지니어 | 12페이지에서도 계속, **360건+** |

`--category-preset dev`가 둘 다 받습니다. **H0만 쓰면 임베디드·R&D 직무를
놓칩니다** — Embedded S/W Engineer, SW Engineer (R&D) 같은 공고가 N0에 있습니다.

같은 공고가 두 대분류에 태깅될 수 있고, 그때 상세는 한 번만 받습니다
(`distinct_postings_seen`과 `duplicate_rows`로 manifest에 기록).

## 광고 슬롯은 목록 행이 아닙니다

한 페이지의 `/recruit/view/` 링크 수와 실제 공고 수가 크게 다릅니다.

| 페이지 | 링크 | **실제 행** |
|---|---|---|
| 1 | 68 | **30** |
| 8 | 19 | **17** |
| 9 이후 | 2 | **0** |

배너·사이드바 슬롯이 링크를 만들고, 그 id는 **회전합니다.** 링크를 세는 방식은
9·10·11·12페이지에서 매번 "새 공고" 1~2건을 찾아내서 **목록의 끝을 영원히 못
봅니다.**

파서는 `<td>`가 5개 이상이고 상세 링크가 있는 `<tr>`만 취합니다. 그러면 9페이지가
0행으로 파싱되고 그게 이 수집기의 중단 조건입니다.

## 목록이 등록일 순이 아닙니다

H0 2페이지의 공고가 1페이지보다 **오래됐습니다**(2026-06-15 ~ 07-02 대 최신).
그래서 범위 밖 페이지에서 조기 중단하지 않습니다 — 목록 전체를 읽고 날짜 필터를
행 단위로 적용합니다. 등록일에 대한 서버측 필터는 없습니다.

## 시작일을 등록일로 저장하지 않습니다

상세 페이지가 `시작일 2026.07.02 13:00`을 표기하고, 실측한 공고에서는 목록의
`(2026-07-02 등록)`과 우연히 같았습니다. 그래도 **다른 필드입니다** — 시작일은
접수 시작이고 등록일이 아닙니다.

`job.collector.normalize._posted_at_for`가 상세 timestamp를 목록 컬럼보다
우선하므로, 시작일을 `posted_at`으로 올리면 **미리 예약 등록된 공고마다 접수일이
등록일로 저장됩니다.** S15P21E102-148이 기록한 그 실패입니다. 그래서
`parse_detail`은 `posted_at`을 반환하지 않고, 라벨이 붙은 목록 컬럼을 씁니다.

## 본문은 `jp_content` 하나입니다

`div.jp_content` 안에 `role_desc`·`etc_desc`·`org_desc`·`notice_desc`가 있는데,
**섹션 컨테이너가 아닙니다.**

- 한 페이지에 `role_desc`가 3번 반복됩니다
- 전부 `jp_content` 안에 중첩돼 있습니다
- **이름과 내용이 맞지 않습니다** — 실측한 `role_desc` 하나에 "보상 연봉 : ..."이
  들어 있었습니다

고용주가 직접 쓴 HTML 템플릿의 클래스명입니다. 섹션으로 읽으면 본문이 2배가 되고
라벨이 거짓이 됩니다. 그래서 전체를 담은 컨테이너 하나만 읽습니다.

## 직종 태그는 필터가 아닙니다

`span.otNm`이 공고당 최대 7개의 직종 태그를 답니다. 실측한 Product Owner 공고에
`#웹프로그래머`·`#응용프로그래머`·`#서버.보안.네트워크.DB`가 모두 붙어
있었습니다. 고용주가 다중 선택한 것이라 노이즈가 큽니다.

`raw_job_category`에 사이트가 쓴 그대로(`#` 포함) 저장하고, 필터로는 쓰지
않습니다. 좁히는 일은 서버측 `i_jc1`이 합니다. 기술 멘션으로 승격하지도 않습니다 —
사이트 태그에 맞는 `SourceSurface`가 없습니다.

## 실행

```bash
cd AI
python -m Career_Collector_V1 \
  --start-date 2026-01-01 --end-date 2026-09-09 \
  --category-preset dev \
  --max-pages 40 \
  --cursor ../data/career/cursor.json \
  --output-dir ../data/career
```

주요 옵션:

| 옵션 | 뜻 |
|---|---|
| `--category-preset dev` | H0+N0. `it`은 H0만 |
| `--category H0,N0` | 대분류 코드 직접 지정 (프리셋과 합쳐집니다) |
| `--days-back N` | `--end-date` 기준 N일 전까지 (예약 회차용) |
| `--no-detail` | 목록만. 레코드는 `body_status=MISSING` |
| `--page-size` | 목록 행 수. 사이트 선택기가 5~30을 제공하고 기본 30 |
| `--no-upload-raw` | HDFS 적재 생략 |

### 출력

`{output-dir}/{pipeline_run_id}/` 아래 3개입니다.

| 파일 | 내용 |
|---|---|
| `job_analysis_input.json` | 검증된 계약 배치 |
| `postings.csv` | 분석용 평면 CSV |
| `manifest.json` | 회차 계측 + `source_admission` |

### HDFS Raw

`WEBHDFS_URL`이 설정돼 있으면 회차 종료 후 자동 적재됩니다
(`job/collector/raw_sink.py`). **컨테이너 안에서 실행해야 합니다** — NameNode가
DataNode 호스트명으로 307 리다이렉트하고 그 이름은 호스트에서 해석되지 않습니다.

```powershell
docker compose ... run --rm --no-deps `
  -v "$repo\data:/data" -v "$repo\AI:/app" `
  collector python -m Career_Collector_V1 ...
```

### 커서

`--cursor`를 주면 이미 수집한 공고 id를 건너뜁니다. 날짜 범위가 바뀌면 커서는
버려집니다.

커서는 **`write_outputs`가 배치를 디스크에 쓴 다음에만** 저장됩니다
(S15P21E102-174). 크롤 중에 저장하면 중단된 회차가 데이터를 영구히 잃습니다 —
커서는 수집했다고 주장하는데 배치가 없고, 재실행이 커서를 믿고 조용히
건너뜁니다. 사람인이 이 방식으로 3,072건을 잃었습니다.

## 스케줄

`schedule.toml`에 `career-morning`(10:10)·`career-evening`(22:10)이 선언돼 있고
**둘 다 `enabled = false`**입니다. 이유는 위 「기준 A 미통과」 절에 있습니다.

게임잡보다 20분 늦게 잡은 것은 네 수집이 같은 시각에 겹치면 사이트별 간격(2초)을
지켜도 우리 쪽 부하가 겹치기 때문입니다.

## 날짜 파싱에서 주의할 점

등록일이 세 갈래입니다.

```
(2026-07-02 등록)    절대 — 연도가 있습니다
(13시간 전 등록)      상대
(6일 전 등록)         상대
```

절대 표기에 연도가 있는 것이 게임잡과 다른 점입니다(게임잡은 `07/28(화) 등록`).
연도가 있으면 추론이 필요 없고 우리 시계와 사이트 시계 차이에 흔들리지 않으므로
절대 표기를 먼저 시도합니다.

마감일은 두 갈래입니다.

```
상시채용             날짜가 되지 않습니다. 파싱하면 열린 공고가 CLOSED 가 됩니다
~10/01(목)           연도가 없습니다 — 앞쪽으로 추론
```

**등록일과 마감일은 연도를 반대 방향으로 추론합니다.** 등록일은 미래일 수 없고,
살아 있는 목록의 마감일은 보통 앞에 있습니다. 하나의 추론을 공유하면 공고가 1년씩
조용히 이동합니다.
