# 잡코리아 존치 여부 판단 근거

> 상태: 결론 확정 — **제외**
>
> 작성일: 2026-08-31
>
> 대상: A조 / P1 축 / 기능명세서 v3 `AF1`
>
> 관련 문서: [데이터 플랫폼·파이프라인](README.md)

## 1. 결론

잡코리아를 채용공고 수집 source에서 **제외한다.** 파서를 신규 작성하지 않고, 1차 검증에 사용한 수집 코드와 저장 표본을 폐기한다.

독립적인 근거 3개가 같은 결론으로 수렴한다. 이 중 §3.1(법적 근거)은 Coverage 수치와 무관하게 단독으로 제외 사유가 된다.

| 근거 | 내용 | 단독 제외 성립 |
|---|---|---|
| §3.1 법적 | 잡코리아 채용공고 무단 크롤링은 판례가 DB제작자 권리 침해로 확정한 행위 유형 | 성립 |
| §3.2 공식 경로 | 잡코리아 API는 신입공채·공공기관/학교 한정으로 GitJob 용도와 불일치 | 성립 |
| §3.5 집계 정합성 | 저 Coverage source 존치가 다른 source의 수요 비율까지 왜곡 | 조건부 |
| §3.4 비용 | Coverage 30%, 공고당 평균 기술 0.50개 | 미성립(보조) |

## 2. 티켓 전제에 대한 수정

착수 메모의 “추가 표본으로 Coverage 재측정”은 **수행하지 않을 것을 권고한다.**

재측정에는 잡코리아 공고의 추가 크롤링이 필요하고, 그 행위 자체가 §3.1 판례가 침해로 인정한 행위다. 재측정은 결론을 바꾸지 못하면서 노출 표본만 늘린다. 따라서 이 티켓은 “재측정 후 판단”이 아니라 “수집 정당성 심사로 종결”한다. 1주 예정 작업이 재측정 없이 닫힌다.

## 3. 근거

### 3.1 법적 근거 — 단독으로 결정적

잡코리아와 사람인 사이의 9년 소송에서, 서울고등법원은 사람인이 잡코리아의 채용정보를 허락 없이 크롤링해 자사 영업에 이용한 행위를 **저작권법 제93조 1·2항 위반, 잡코리아의 데이터베이스제작자 권리 침해**로 판단했다. 간접강제금 2억 원과 손해배상 2억 5천만 원을 합해 4억 5천만 원 지급이 선고되었고, 별건으로 사람인에이치알이 합의금 120억 원을 지급했다. 대법원도 크롤링으로 확보한 콘텐츠를 자신의 영업에 무단 사용하는 것을 DB권 침해로 판시했다.

GitJob이 하려는 행위와의 대응 관계:

| 판례가 인정한 침해 행위 | GitJob의 계획 |
|---|---|
| 경쟁사 채용정보를 허락 없이 크롤링 | 잡코리아 공고 목록·상세를 파서로 수집 |
| 자사 영업에 이용 | 기술 추출 후 `job_demand_snapshot` 집계에 사용 |

행위 구조가 동일하다. 서비스가 비영리·교육 목적이라는 점은 DB제작자 권리 침해 판단에서 면책 사유로 보장되지 않는다.

**robots.txt는 근거가 되지 못한다.** 잡코리아 robots.txt의 와일드카드 블록은 공고 상세 경로(`/Recruit/GI_Read`)를 `Allow`하고 있어 형식상 허용처럼 보인다. 그러나 위 판례는 robots.txt가 아니라 저작권법상 DB권을 근거로 한다. 오히려 같은 robots.txt는 `ClaudeBot`, `GPTBot`, `CCBot`, `Diffbot`, `DeepSeekBot` 등 AI·스크래퍼 User-agent를 명시적으로 `Disallow: /` 처리하고 있어, 수집 목적 봇에 대한 사이트의 의사는 거부에 가깝다. “robots.txt가 막지 않았으므로 수집해도 된다”는 논리는 이 사안에서 성립하지 않는다.

### 3.2 공식 경로 부적합

잡코리아는 채용정보 API를 제공하지만 GitJob 용도와 범위가 맞지 않는다.

| 항목 | 잡코리아 API | GitJob 요구 |
|---|---|---|
| 공고 범위 | 신입공채 한정 | 직무별 전체 공고 |
| 제공 대상 | 공공기관 또는 학교 | 해당 없음 |
| 거절 조건 | 사용목적 불분명·미오픈 사이트는 제공 불가 | — |
| 승인 절차 | 담당자 확인 후 IP 등록·고유 링크 발급 | — |

신입공채로 범위가 고정되면 경력·직무별 기술 수요 집계라는 `AF1`의 목적을 충족할 수 없다. 따라서 “크롤링 대신 공식 API로 우회”라는 대안도 성립하지 않는다.

### 3.3 대안 source가 정식 경로를 갖는다

잡코리아를 제외해도 정식 라이선스 경로를 가진 source 2개가 남는다. source 0개가 되는 상황이 아니다.

| Source | 정식 경로 | 한도 |
|---|---|---|
| 사람인 | 오픈 API (`oapi.saramin.co.kr`), 이용신청·승인 필요 | 일 최대 500회 호출 |
| 워크넷 | 공공데이터 기반 수집 | [README](README.md) §3 기준 일 명목 1,000건 |

### 3.4 산출 대비 비용 — 보조 근거

1차 검증 인용 수치다. 원본 산출물이 레포에 없어 재검증하지 않았다(§6).

| 지표 | 값 |
|---|---|
| 기술 Coverage | 30% |
| 공고당 평균 기술 | 0.50개 |

공고 10건을 수집해도 기술 신호가 있는 공고는 3건, 추출 기술은 5개다. 파서 4개를 2명이 유지하는 구성에서 잡코리아는 산출 최하위이며, 파서 1개를 줄이면 유지 대상이 3개로 내려간다.

이 수치는 §3.1이 이미 결론을 확정한 뒤의 보조 근거다. Coverage가 90%였더라도 §3.1 때문에 결론은 제외로 동일하다.

### 3.5 집계 정합성 — 존치가 다른 source를 오염시킨다

[README](README.md) §9는 “job demand는 중복 공고를 deduplicate한 분모와 기간을 함께 표시한다”, “서로 다른 출처를 weighted score로 합치지 않는다”로 정하고 있다.

Coverage 30% source를 공통 분모에 넣으면 기술 신호가 없는 공고 70%가 분모를 부풀려 **모든 기술의 수요 비율이 하향 왜곡된다.** source별 분모를 완전히 분리해 저장·응답하지 않는 한, 잡코리아 존치는 단순한 유지비 낭비가 아니라 사람인·워크넷의 수요 비율 정확도까지 손상시킨다. 이는 요구사항의 “근거 없는 수치를 노출하지 않는다” 원칙과 정면으로 충돌한다.

## 4. 판단 기준

결론이 사후 합리화가 아님을 보이기 위해 기준을 명시한다. 다른 source 심사에도 같은 기준을 적용한다.

| 기준 | 내용 | 잡코리아 |
|---|---|---|
| A. 수집 정당성 | 정식 수집 경로가 없거나 판례·약관상 금지되면 Coverage와 무관하게 제외 | 해당 → **제외 확정** |
| B. 산출 | Coverage < 60% 또는 공고당 평균 기술 < 1.5개면 제외 후보 | 해당 |
| C. 집계 정합성 | source별 분모 분리가 구현되지 않은 상태에서 저 Coverage source 존치 금지 | 해당 |

기준 A는 B·C보다 상위다. A에 걸리면 B·C를 측정하지 않는다.

## 5. 수집 실패·차단 빈도 기록

추가 수집을 수행하지 않기로 했으므로 이 항목은 **N/A로 종결한다.** 1차 검증에서 관측된 실패·차단이 있다면 §6의 원본 산출물에 남기고, 신규 측정은 하지 않는다.

향후 다른 source에 같은 판단이 필요할 때 사용할 기록 스키마만 남긴다.

```text
source, attempted_at, url_pattern, http_status,
block_type    = ROBOTS | WAF | CAPTCHA | RATE_LIMIT | LOGIN_WALL,
retry_after,
body_state    = TEXT_AVAILABLE | IMAGE_ONLY | BLOCKED | MISSING | PARSE_FAILED
```

`body_state`는 [README](README.md) §6의 본문 상태 값을 그대로 사용해 정규화 단계와 어휘를 통일한다.

## 6. 이 문서가 채우지 못한 것

| 항목 | 상태 | §3.1 결론에 영향 |
|---|---|---|
| 1차 검증 원본 | Coverage 30%·평균 0.50개의 표본 목록, Coverage 정의(분자/분모), 측정일이 레포에 없음. 노션 또는 로컬 산출물 링크를 이 절에 추가해야 한다 | 없음 |
| 파서 4개의 구성 | 잡코리아 외 3개가 무엇인지 미확인. [README](README.md) §3은 워크넷·사람인 2개만 명시한다 | 없음 |

두 항목 모두 §3.4의 보조 근거에만 관련되며, 제외 결론은 이 값들 없이 성립한다.

## 7. 후속 작업

1. [README](README.md) §3 수집 대상 표에 잡코리아가 없음을 확인한다. 현재도 미포함이므로 문서 변경은 불필요하다.
2. 1차 검증에 사용한 잡코리아 수집 코드와 저장 표본을 폐기한다.
3. 사람인 오픈 API 이용신청을 진행한다. 승인 절차가 있어 리드타임을 일정에 반영한다.
4. 사람인 일 500회 호출 한도가 [README](README.md) §3의 “일 단위 수집” 계획에 충분한지 재확인한다. 목록·상세를 분리 호출하면 한도 소진이 빠르다.
5. 파서 4개 중 잡코리아 외 나머지 구성을 확인하고, 각 source에 §4 기준 A를 동일하게 적용한다.

### 9.1 §7-2 가 남아 있다 — 수집 코드가 아직 레포에 있다

§1 이 "1차 검증에 사용한 수집 코드와 저장 표본을 폐기한다"고 결론했는데,
`AI/JobKorea_Collector_V1/` 이 **파일 10개로 develop 에 그대로 있다.**
`schedule.toml` 에 회차 선언이 없어 자동으로 돌지는 않는다.

폐기하려면 참조도 함께 정리해야 한다.

```text
AI/README.md                              수집기 목록
AI/Worknet_Collector_V1/README.md         선례 참조
AI/Worknet_Collector_V1/crawler.py        선례 참조
AI/job/collector/__init__.py              공용 계층 docstring
AI/job/fixtures/job_analysis_input_v1.json          계약 fixture
AI/job/fixtures/invalid_job_analysis_input_v1.json  계약 fixture
AI/tests/test_intake_producer_compat.py
AI/tests/test_job_classifier.py
AI/tests/test_job_collector.py
AI/tests/test_job_contracts.py
```

**계약 fixture 두 개가 판단을 필요로 한다.** `-90` 이 고정한
`job-analysis-input/v1` 의 합성 fixture 에 `JOBKOREA` 가 `source_site` 값으로
들어 있다. 수집기를 지우는 것과 계약 fixture 에서 사이트 이름을 빼는 것은 다른
일이고, fixture 를 건드리면 `-90` 계약 테스트가 함께 바뀐다.

즉 §7-2 는 "디렉터리 삭제"가 아니라 별도 티켓이 필요한 작업이다. 이 문서는
그 사실만 기록하고 결정하지 않는다.

### 9.2 §7-5 는 완료됐고 두 번 더 적용됐다

§4 기준 A 를 신규 후보에 적용한 기록이
[`-149` 채용 source 후보 기준 A 심사](2026-09-08-source-criterion-a-review.md)에
있다. 이 문서의 §4 가 그 심사의 기준 문서다.

| 후보 | 판정 | 근거 |
|---|---|---|
| 게임잡 | 미통과 | 운영사가 **잡코리아와 동일 법인**(110-81-34859). §3.1 의 판례 근거가 그대로 적용 |
| 링커리어 | 미통과 | 이용약관 제20조가 크롤링·스크래핑을 명시적으로 금지 |
| 커리어 | 미통과 | 이용약관 제14조 5항이 동의없는 복제·배포를 금지. robots.txt 는 허용 |
| 자소설닷컴 | 판정 불가 | 약관 페이지가 SPA 라 본문 확인 실패 |
| 공공데이터 채용 API | **통과** | 정식 경로, 이용허락범위 제한 없음 |
| 고용24 | 해당 없음 | **이미 수집 중** — 워크넷 수집기의 `base_url` 이 `work24.go.kr` 이다 |

**게임잡이 §3.1 을 그대로 물려받은 사례가 이 문서의 실질적 효용이다.** 운영사가
잡코리아와 같은 법인이라는 사실 하나로 별도 판례 조사 없이 판정됐다.

게임잡·커리어는 기준 A 미통과인데 **수집기가 구현돼 있다.** 소유자가 조항을
확인한 뒤 진행을 결정한 것이고, 두 사이트 모두 `schedule.toml` 에서
`enabled = false` 이며 회귀 테스트로 고정돼 있다. 근거는 각 수집기 README 와
회차 manifest 의 `source_admission` 에 기록된다.

### 9.3 §3.5 의 우려는 실측으로 확인됐다
