## 1. 전체 그림 한 장

```text
   [수집]                    [원본 저장]              [전달]           [분석]

 워크넷 ─┐
 사람인 ─┤                  ┌──────────────┐
 게임잡 ─┼─→ 수집기 4종 ──→ │  HDFS Raw    │ ←── 원본의 기준
 잡코리아┘   (하루 2회)      │  (불변·영구) │
                            └──────┬───────┘
 GH Archive ─→ 수집기 ─────────────┤
 GitHub Repo ─→ 수집기 ────────────┘
                                   │
                      "회차가 끝났다" 알림만
                                   ↓
                          ┌─────────────────┐
                          │ Kafka           │
                          │ jobs.collected  │
                          └────────┬────────┘
                                   ↓
                      C1 적재 · C2 추출 · C3 집계
                              (아직 없음)
```

**핵심 한 줄: 공고 원문은 HDFS에 있고, Kafka는 "회차가 끝났다"는 사실만 나릅니다.**

## 2. Kafka를 왜 쓰는가 — 그리고 어디에는 안 쓰는가

### 2.1 쓰는 이유

Kafka는 **한 데이터를 여러 소비자가 각자의 속도로 읽어야 할 때** 값을 냅니다. 우리 프로젝트에서 그게 성립하는 건 주로 GitHub 쪽입니다.

| 조건 | 설명 |
|---|---|
| 여러 소비자 | 같은 event를 C1(적재)·C2(기술추출)·C3(집계)가 각자 읽음 |
| 속도 차이 | GH Archive는 시간당 57.8만 event 버스트, 소비는 훨씬 느림 |
| 되감기 | 특정 시점부터 다시 읽는 것이 복구 절차 (`cleanup.policy=delete`) |
| 장애 격리 | 소비자가 죽어도 수집은 계속됨 |

### 2.2 안 쓰는 곳

**Stack Overflow Dump는 Kafka를 통과하지 않습니다.** 수십 GB를 브로커로 흘릴 이유가 없어 HDFS 직행입니다. 원래 파티션 설계(`posts.raw` 6개)가 이 전제였는데, 직행으로 바뀌면서 부하 프로파일이 뒤집혔습니다 — 이제 큰 쪽은 `github.events`입니다.

### 2.3 채용공고는 미묘합니다 — 구현은 A안, 회의 확인은 남았습니다

채용공고는 위 조건 중 어느 것도 뚜렷하게 성립하지 않습니다.

- 유입: 하루 2~4회 배치, 약 600건/일 (GH Archive 대비 네 자릿수 적음)
- 실시간 소비자: **없음**. 기술추출·수요집계 모두 배치
- 속도 차이: 없음

그래서 두 가지 설계가 경쟁했습니다.

| | **A안 (채택)** `jobs.collected` | B안 `jobs.raw` |
|---|---|---|
| 회차당 메시지 | **1건** | 레코드 수 + 1건 |
| 4,631건 백필이면 | **1건** | **4,632건** |
| 공고 본문 | HDFS에만 | Kafka payload에 |
| 싣는 것 | run 위치 + 건수 (Claim Check) | 공고 원문 |

**구현은 A안으로 갔습니다.** 근거는 이렇습니다.

- 채용공고는 **가변 상태의 주기적 스냅샷**입니다. 같은 공고가 수정되면 새 `content_hash`로 다시 관측됩니다. append-only 이벤트가 아닙니다
- 반면 **"회차 완료"는 한 번 일어나면 불변이고 순서가 의미 있는** 진짜 이벤트입니다. A안이 싣는 게 그것입니다
- 원문을 Kafka에 넣으면 HDFS와 사본이 둘로 갈라지고, retention 7일이 지나면 어긋납니다

`-103`이 A안을 구현했고 이미 develop에 머지됐습니다(`24d7837`). B안 구현체는 오늘 삭제했고, `jobs.collected` 토픽도 만들었습니다.

> **회의 확인이 남았습니다.** `-102` 문서는 이 선택을 "회의 결정 사항"으로 두고 있고, 확인 체크리스트 9개가 아직 열려 있습니다(`- [ ] ① … - [ ] ⑨`). 지금 상태는 **구현이 A안으로 굳었고 문서상 합의는 미완**입니다. 파티션 3은 되돌리기 어려우므로 이 항목부터 확인받는 게 좋습니다.

> **후속 필요**: `docs/data/README.md` §3의 워크넷·사람인 행이 아직 `jobs.raw`를 가리킵니다. 게임잡 행만 `jobs.collected`로 고쳐 놨습니다. 나머지는 `-102`와 함께 정리해야 합니다.

## 3. 오늘 만든 Kafka 구성

### 3.1 토픽

```
Topic: jobs.collected
PartitionCount: 3   ReplicationFactor: 1
Configs: cleanup.policy=delete, retention.ms=-1
```

| 값 | 이유 |
|---|---|
| 파티션 **3** | 메시지 키가 `source_site`입니다. **같은 사이트 회차의 순서 보장**을 키로 얻으려면 최소 사이트 수만큼 필요하고, 사이트가 늘 수 있어 3 |
| `retention.ms=-1` | 무기한. 되감아 다시 읽는 것이 복구 절차 |
| `cleanup.policy=delete` | `compact`가 아닌 이유도 같습니다 — 특정 시점 되감기가 목적 |

**`github.events`·`so.raw`는 일부러 만들지 않았습니다.** `-102` 문서의 파티션 확정 체크박스(`- [ ] ⑤ 파티션 6/3/3 확정`)가 아직 열려 있습니다. 파티션은 **줄일 수 없고**, 늘리면 키 해시가 재배치돼 순서 보장이 깨집니다. 지금 필요 없는 것을 되돌릴 수 없게 고정하지 않았습니다.

### 3.2 메시지 모양 — 실측

아래는 **브로커에서 직접 꺼낸 실제 메시지**입니다 (2026-09-08 22:28 발행).

```json
key: gamejob
{
  "schema_version": "1",
  "source": "gamejob",
  "source_id": "GAMEJOB-20260908T111133Z",
  "event_type": "job.collection.completed",
  "occurred_at": "2026-09-08T11:13:00+00:00",
  "ingested_at": "2026-09-08T13:28:15.539039+00:00",
  "event_id": "jobs-GAMEJOB-20260908T111133Z",
  "payload": {
    "run_name": "gamejob-backfill-publish-test",
    "site": "GAMEJOB",
    "pipeline_run_id": "GAMEJOB-20260908T111133Z",
    "record_count": 18,
    "status": "SUCCESS",
    "run_path": "/gitjob/raw/gamejob/dt=2026-09-08/GAMEJOB-20260908T111133Z",
    "files": [
      "hdfs:///gitjob/raw/.../job_analysis_input.json",
      "hdfs:///gitjob/raw/.../postings.csv",
      "hdfs:///gitjob/raw/.../manifest.json"
    ],
    "collector_version": "gamejob-collector/v1",
    "dataset_snapshot_id": "GAMEJOB-2026-07-01-2026-09-08"
  }
}
```

**공고 18건이 메시지 1건입니다.** payload에 공고가 없고 `run_path`만 있습니다 — Claim Check가 실제로 그렇게 동작한다는 뜻입니다.

메시지 키가 `gamejob`(= `source_site`)인 것도 확인됩니다. 파티션 3의 근거가 이 키입니다.

읽는 쪽이 알아야 할 두 가지:

- **`event_id`가 난수가 아닙니다.** 회차 id에서 파생하므로 같은 회차를 재발행하면 같은 id가 나옵니다. **중복 제거는 소비자 책임**입니다
- **적재가 실패한 회차는 발행되지 않습니다.** event가 HDFS를 가리키므로, 가리킬 대상이 없으면 보내지 않습니다. 반대로 발행이 실패해도 수집은 성공으로 남습니다

### 3.3 발행 주체

**수집기가 아니라 스케줄러가 발행합니다.**

```
python -m job.collector --run worknet-morning
   → 수집기 실행 (subprocess)
   → HDFS Raw 적재
   → 실행 이력 기록
   → jobs.collected 발행          ← 여기
```

그래서 개별 수집기(`GameJob_Collector_V1` 등)에는 Kafka 코드가 **없습니다.** `schedule.toml`에 선언되는 것만으로 발행 대상이 됩니다.

## 4. 오늘 한 크롤링 작업

### 4.1 게임잡 수집기 추가

네 번째 채용공고 수집기입니다. 구현·검증 완료, MR 대기 중(`-171`).

**워크넷·사람인과 다른 점 세 가지** — 이게 이 사이트의 특징입니다.

**① 서버측 필터·정렬이 query string으로 안 먹습니다**

`?duty=1`·`?orderTab=3`·`?psTab=40`·`?Page=N` 전부 무시됩니다. 필터 없는 요청과 **바이트 단위로 동일한** 응답(364,189 B)이 옵니다. 세션에 POST되고 목록이 세션 상태로 다시 렌더링되는 구조입니다.

**그래서 `?Page=N`도 페이징하지 않습니다.** 80페이지를 요청해 3,200행을 받았는데 고유 공고는 **40건**이었습니다 — 모든 페이지가 같은 페이지입니다.

> 목록 1페이지가 게임잡의 전부입니다. 40건.

수집기는 새 공고 id를 주지 않는 페이지에서 중단합니다. 회차당 목록 요청이 10번에서 2번으로 줄었습니다.

**② 본문이 iframe에 있습니다**

상세 페이지에 본문 텍스트가 없고 iframe 두 개(담당업무·자격조건)를 받아야 합니다. **공고 1건 = 최대 3요청**입니다. 요청 간격을 낮추지 않는 이유입니다.

**③ 절반이 이미지 공고입니다**

실측 18건 중 `IMAGE_ONLY` 6건 / `TEXT_AVAILABLE` 12건. 게임업계 특성상 본문이 이미지 한 장인 공고가 많습니다. **권한 없는 OCR은 하지 않으므로** 그 공고는 본문 0자로 남고 기술 추출이 불가능합니다.

### 4.2 HDFS 적재를 실제로 확인했습니다

지금까지 `raw=skipped`(WEBHDFS 미설정)로만 돌았는데, 오늘 처음 실제 적재를 검증했습니다.

```
/gitjob/raw/gamejob/dt=2026-09-08/GAMEJOB-20260908T111133Z/
  job_analysis_input.json   49,858
  postings.csv               8,439
  manifest.json              2,530
```

`docker cp`로 원본을 꺼내 확인: **계약 검증 통과**, **sha256이 로컬 사본과 일치**.

**여기서 중요한 것을 발견했습니다.** WebHDFS 쓰기는 NameNode가 DataNode로 307 리다이렉트하는데, Location이 컨테이너 호스트명(`hdfs-datanode`)이라 **호스트에서는 DNS 해석이 안 됩니다.** 수집을 **컨테이너 안에서** 돌려야 적재가 됩니다.

같은 이유로 `KAFKA_BOOTSTRAP_SERVERS`도 `.env.wsl`에만 있어 호스트 실행에서는 발행이 건너뛰어집니다.

> 이게 실측으로 드러난 사례가 있습니다. 어제 21:10 워크넷 예약 회차가 **493건을 수집했지만 HDFS에는 안 올라갔습니다.** 호스트에서 실행됐기 때문입니다. 예약 작업을 컨테이너 경유로 바꾸는 것이 다음 작업입니다.

### 4.3 스케줄 자동화

Windows 작업 스케줄러에 5개 등록했습니다.

| 시각 | 작업 |
|---|---|
| 09:10 / 21:10 | 워크넷 수집 |
| 09:30 / 21:30 | 사람인 수집 |
| 11:45 / 23:45 | **결번 검사** |

결번 검사 시각은 `max_interval_hours = 14`에서 나옵니다. 저녁 회차 21:30 성공 → 결번 선언 시점이 익일 11:30이므로 11:45 검사가 실패한 아침 회차를 잡습니다. 수집 직후(10:00)에 돌리면 아직 14시간이 안 지나서 실패를 못 잡습니다.

> **주의**: 작업 스케줄러 기본값이 **배터리에서 실행을 막습니다**(`DisallowStartIfOnBatteries`). 처음 등록했을 때 이 때문에 작업이 15분간 `Queued`에서 멈춰 있었습니다. `-AllowStartIfOnBatteries`가 필요합니다.

### 4.4 사람인 백필 — 실패했고, 그 원인이 중요합니다

2개월 창으로 백필을 돌려 46/100 페이지에서 **2,287건**을 모았습니다. 그런데 전원 종료로 **전부 잃었습니다.**

원인은 수집기 공통 구조입니다.

```
crawler.py:314   cursor.save()        ← 페이지마다 저장
crawler.py:645   write_outputs(...)   ← run() 종료 후 한 번만
```

**커서는 페이지마다 저장되는데 공고 데이터는 마지막에 한 번 씁니다.** 강제 중단이 곧 영구 손실입니다 — 커서에는 "수집 완료"로 남아서 재개 시 조용히 건너뜁니다.

**워크넷·사람인·게임잡 전부 같은 구조입니다.** 2시간 넘는 백필을 안전하게 돌릴 수 없습니다. 티켓이 필요합니다.

## 5. 다른 팀이 알아야 할 제약 ★

### 5.1 과거 공고는 크롤링으로 가져올 수 없습니다

**기술스택 변화 분석을 맡은 쪽은 이걸 먼저 읽으십시오.**

실측: 워크넷에 `2026-02-01 ~ 2026-03-31`을 요청 → **0건, "listing exhausted"**

채용 사이트 목록에는 **아직 열려 있는 공고만** 있습니다. 마감되면 목록에서 사라지고 아카이브가 없습니다. 워크넷은 등록일 범위를 서버측 파라미터로 받는데도 0건입니다.

| 원하는 것 | 실제 가능한 것 |
|---|---|
| 과거 N년 기술스택 추이 | 등록일 기준 **약 2개월** 스냅샷 1장 |
| 시계열 비교 | **오늘부터 축적**해야 생김 (하루 2회 × N일) |

지금 가진 것은 워크넷 백필 4,631건(2026-07-10~09-08)이 전부입니다. 한 달 뒤엔 1개월치 시계열이, 세 달 뒤엔 3개월치가 생깁니다. **지금 당장 3년치를 만들 방법은 없습니다.**

### 5.2 사이트별 실제 상한과 수집 정당성

| 사이트 | 상한 | 기준 A (`-149`) |
|---|---|---|
| 워크넷 | **4,631건** (실측, 2개월) | 통과 |
| 사람인 | 미측정 (46페이지에서 2,287건, 진행 중 중단) | 통과 |
| 게임잡 | **40건** | **미통과** |
| 자소설닷컴 | — | **판정 불가** (약관 페이지가 SPA) |
| 링커리어 | — | **미통과** (약관 제20조 크롤링 금지) |
| **공공데이터 채용 API** | — | **통과**. 크롤링 아님 → 차단 위험 없음 |

**볼륨을 늘리려면 공공데이터 채용 API가 정답입니다.** `-161`에서 개발계정을 신청 중입니다. 다만 응답에 자격요건·기술스택 필드가 없어 기술 수요 집계에 쓸 수 있는지는 표본 확인이 남았습니다(기준 B).

### 5.3 게임잡은 기준 A 미통과 상태로 대기 중입니다

`-149` 심사가 게임잡을 미통과로 판정했습니다. 운영사 웍스피어가 **잡코리아와 동일 법인**(사업자등록번호 `110-81-34859`, 앱 패키지명 `com.jobkorea.gamejob`)이라 `-94`의 판례·소송 근거가 그대로 적용됩니다.

수집기는 구현했지만 `schedule.toml`에서 `enabled = false`이고 **회귀 테스트가 이를 고정합니다**(`test_gamejob_is_declared_but_never_scheduled`). 켜는 전제는 웍스피어와의 데이터 제공 계약입니다.

### 5.4 기술 신호를 가장 크게 늘릴 수 있는 지렛대

게임잡 상세에 `키워드` 행이 있습니다 — `서버, Unreal, Unity, MS-SQL, 게임프로그래밍`.

실측 18건 회차에서 **사이트 키워드 195건 / 규칙 기반 추출 8건**. 24배 차이입니다.

저장하지 않는 이유는 `job.contracts.SourceSurface`가 `TITLE | BODY`뿐이라 사이트 자체 태그를 기록할 surface가 없기 때문입니다. `BODY`로 저장하면 공고 본문이 하지 않은 말을 했다고 주장하게 됩니다. **`SITE_TAG` surface 추가는 `-90` 계약 변경 사안**이고, 사람인에도 같은 필드가 있어 효과가 전 사이트에 적용됩니다.

### 5.5 Kafka 소비자가 아직 없습니다

`KafkaConsumer` 코드가 코드베이스에 **0건**입니다. BE Java 30개 파일에도 없습니다.

**발행은 검증됐지만 읽는 쪽이 없습니다.** 지금 `jobs.collected`에 메시지 1건이 쌓여 있고 아무도 소비하지 않습니다. `-112`(컨슈머 그룹 3종 실행 골격)가 그 작업입니다.

그 메시지는 `-112` 개발용 샘플로 그대로 남겨 뒀습니다. `--from-beginning`으로 읽으면 실제 봉투 구조를 볼 수 있습니다.

```powershell
docker exec gitjob-kafka-1 /opt/kafka/bin/kafka-console-consumer.sh `
  --bootstrap-server localhost:9092 --topic jobs.collected `
  --from-beginning --max-messages 1 --timeout-ms 20000 --property print.key=true
```
